The plan is thorough and its architecture is sound, but it has some gaps. One premise is also contradicted by this repo.

**The game source exists, and it already ships.** This workspace is a React + Vite + Capacitor app with `ios/` and `android/` projects. It uses RevenueCat (`@revenuecat/purchases-capacitor`), and its README describes a premium subscription and on-device Apple Foundation Models board generation. That conflicts with several plan assumptions:

- Step 1 says no game source was found and to inspect it before importing it into Rork. This repo is that source. It is a Capacitor web-view wrapper, not Swift. Rork would be rewriting the UI, not converting it, and your "preserve gameplay and platform behavior" goal means writing a spec from this code first.
- The plan's Out of scope lists paid packs, subscriptions and "A website wrapper … as the App Store game". This app already has a subscription tier, and a Capacitor app is arguably a web wrapper. Decide which of these you mean before writing the scope.
- The AI board creator with Apple Foundation Models is a core feature here. The plan never mentions it, so it needs a decision: port it, or drop it from v1 (which would be a regression).
- Why rewrite natively at all? The plan never compares a native rewrite with adding the release-bundle sync to the existing Capacitor app. The second option is much cheaper, and it should be weighed explicitly. A rewrite is justified only if Capacitor has real problems, such as performance, App Review rejection or the desktop goal.
- None of the plan's "Relevant files" (`artifacts/api-server`, `lib/api-spec`, `BoardsPanel.tsx`, and so on) are in this repo. The API and admin app live in the Replit workspace, so the plan spans at least three repos.

**What's strong**
- Draft versus immutable release is the right core idea. Rollback-as-a-new-increasing-version is the correct approach.
- Using one production database with the duplicate as a dev copy is right, and you state it clearly. GitHub does not sync data.
- The client rules are good: atomic writes, advancing the cursor only after success, and pinning an active game to its version.
- Codex is limited to comments with no merge authority, and the Apple actions stay with you.
- The "downloaded data is not executable code" framing for review notes is correct.

**Gaps and risks**
1. **Ordering.** Step 1 is a gate, so nothing else should start until it is done, and 14 steps in one issue is several projects. I'd split into four:
   - A: API release boundary (steps 2–4)
   - B: Client sync, cache and offline behavior (5–7)
   - C: Ops, privacy and submission (8–12)
   - D: Collaboration setup and website (13–14)

   A can ship and be tested independently before any client exists.
2. **Release schema.** The plan doesn't say how a release is stored. I'd store an immutable `board_releases` row holding the resolved word list as a JSON snapshot, with a content hash and a monotonic per-board version. "Published" becomes a pointer to a release. Add a bundle `schemaVersion` field so old app builds can ignore bundles they can't parse, and define what happens on a breaking change.
3. **Offline withdrawal.** You exclude remote removal, which is fine, but "withdrawn" and "unpublished" need defined client behavior (does it stay visible, flagged as removed?). The same goes for content takedowns caused by a rights problem, where you would want a way to hide the content on next sync.
4. **Download preferences.** Define the matrix of Wi-Fi only, auto-update and manual, plus size caps. It affects the catalog fields, so decide it before step 2.
5. **Rate limits.** The current limits are process-local. If you stay on Replit with several instances they won't hold, so say that rather than only flagging it for Vercel. Since the data is public and read-only, caching headers, ETags and a CDN may be simpler than an API key embedded in the app. An embedded key isn't a secret, so don't treat it as protection.
6. **Subscription and Kids.** If the app stays subscription-based, that affects the age rating and the Kids category (Kids has strict rules on third-party SDKs and purchases). RevenueCat is an SDK you must disclose in the privacy labels. Step 9 should audit it by name.
7. **Rork risk.** The plan treats Rork as fine for Swift output without saying how you'd verify it. Add acceptance criteria such as a gameplay parity checklist and a decision rule for abandoning it. If the generated project can't be maintained in git with clean diffs, the multi-tool PR workflow breaks down.
8. **Desktop.** "Recover desktop support" is vague. Say whether you mean a browser build or a Mac Catalyst or native Mac app. The Capacitor/web code already runs in a browser, so desktop may be nearly free if you keep it.
9. **Missing pieces.** A feature flag or kill switch for the sync client, a way to monitor failed syncs, and fixture-based contract tests (OpenAPI to Swift types) all belong in the plan. Tests need to catch API drift between the Replit repo and the client.
10. **Process.** Three tools writing to one GitHub repo needs explicit rules: one owner per directory or branch prefix, and CODEX/CLAUDE guidance files. You mention these but don't say who owns which repo. Decide that before step 13.

**Recommendation:** Do step 1 first, treating this repo as the source. Answer these three questions before any API work:
- Is the subscription staying?
- Is the AI board creator part of v1?
- Is a native rewrite really needed, or does sync get added to the Capacitor app?

Those answers change steps 5–11 more than anything else. Then split the plan into the four issues above.
